# k6 abuse scenario — the run, 2026-08-06

The evidence for `plans/rebuild/05-security.md` §2:

> - [ ] Rate limits + quota enforcement demonstrated under k6 abuse scenario — **partial.**
>   Both now exist and are unit-tested (`tiers.py` per-account, `rate_limit.py` per-IP on
>   `/v1/catalog`); no k6 run has been done, so the *demonstration* is still owed.

The run has now been done. Harness: `bench/k6/abuse.js`, driven by `bench/k6/run-abuse.sh`.
Both are in the repository and the run is repeatable; this file records one execution and
what it does and does not establish.

## What was run

| | |
|---|---|
| date | 2026-08-06 |
| k6 | v2.1.0 (darwin/arm64) |
| service | `majorana_api.app:create_app` under uvicorn, **one worker**, 127.0.0.1:8000 |
| database | local PostgreSQL 17 in Docker, database `majorana_k6`, migrations at `0048` |
| catalog | provisioned, imported (`accepted=283 rejected=0 dead=0`), attested, published |
| ceilings | the **real defaults**, read out of `rate_limit.py` at run time — 1200/min anonymous, 1 MiB body, free tier 150,000 tokens/week |
| duration | 2m21s, 6866 requests |

The ceilings were not lowered to make the run quick. `run-abuse.sh` greps
`DEFAULT_ANON_LIMIT` out of the source and fails if it cannot read it, so a run that
demonstrated a softened limit is not possible without editing the service.

## Result: every threshold held

```
flood_attempts ....... 3601      flood_served ......... 1200      flood_refused ........ 2401
bystander_served ....... 37      bystander_refused ........ 0
trusted_served ........ 360      trusted_refused .......... 0      trusted_misverdict ..... 0
oversize_refused ....... 12      oversize_accepted ........ 0      ordinary_not_refused .. 12
quota_admitted .......... 5      quota_refused ........... 35      quota_unexpected ....... 0
soak_served .......... 2804      soak_refused ............. 0      server_errors .......... 0
```

`ABUSE SUITE PASSED — every threshold held.`

### The per-IP ceiling is exact

`flood_served` is **1200** against a configured ceiling of **1200**, and
`1200 + 2401 = 3601 = flood_attempts`. Every request after the ceiling was refused and
none before it was. Each refusal carried `application/problem+json`, `reason:
anonymous_rate_limited`, and `Retry-After ≥ 1` — `flood_unexpected` counts any refusal
missing those and is 0.

### And it refused nobody else

`bystander_refused = 0` across 37 reads from a second address, taken **during** the flood
rather than after it. This is the half that matters more than the refusals: the limiter's
failure mode is not an error page, it is `getRepositoryEntries` catching a 429 and quietly
serving the static corpus. A limiter that refused everyone would have satisfied
`flood_refused` perfectly.

### The trusted-caller exemption comes from the token, not the address

`trusted_renderer` ran on the **same address as the flood**, holding the shared secret.
360 requests, **0 refused**, and `X-Majorana-Caller-Trust: trusted` on every one
(`trusted_misverdict = 0`). Since the address was simultaneously being refused 2401 times,
nothing but the token can explain the exemption.

### Quota enforcement is exact under genuine concurrency

**40 concurrent submissions from one free account, 5 admitted, 35 refused, 0 anything
else.** Every refusal carried `reason: run_allowance_exhausted` — the typed plan message,
not the per-IP limiter's `anonymous_rate_limited`, which would have meant the scenario
measured the wrong control.

This is the demonstration the unit tests cannot give. `reserve_execute_run_slot` takes
`SELECT … FOR UPDATE` on the user row precisely because two submissions at the boundary
used to read the same count and both pass; sequential requests exercise the arithmetic and
never touch the lock. Forty separate connections contending on one Postgres row is the
case it was written for, and the boundary held to the unit.

The account is created fresh on every invocation, and the harness asserts `/v1/me` returns
`tier: free` before the storm. Without that assertion the scenario would be decorative:
`local-dev@majorana.test` is in `OPERATOR_IDENTITIES` and is not metered at all, so all
forty submissions would be admitted and the run would report a quota gate that does not
exist.

### Body size, with its control

12 oversized bodies (1 MiB + 4 KB) refused 413, 0 accepted — and 12 ordinary bodies **not**
refused, which is what stops "refuses everything" passing as "enforces a limit".

### Nothing 500'd

`server_errors = 0` across 6866 requests, including 2401 refusals and 40 concurrent writes
contending on one row. The 35.8% `http_req_failed` figure is k6 counting every non-2xx:
2401 rate-limit refusals + 35 quota refusals + 12 × 413 + 12 × 401. All four are the
scenarios working.

## What this run does NOT establish

Written down because a green suite invites the wider reading.

**It is not a capacity measurement, and the latency threshold is deliberately loose.**
`sustained_readers` — 120 concurrent readers on distinct addresses — saw p95 3.62s. That
number is the harness: one uvicorn worker on a laptop sharing a CPU with 120 k6 VUs and
the Postgres container they all read through. **Unloaded, the same 384 KB page answers in
19 ms.** Production is Cloud Run with `--max-instances` from `infra/fleet.env`, and the
renderer reads this route on a 300-second revalidate rather than once per visitor. The
threshold is set at 10s to catch collapse, not to certify throughput. What this scenario
does establish is `soak_refused = 0`: a launch's worth of readers is not refused by the
ceilings above.

**The per-IP limiter is still per-process.** `rate_limit.py` says so: counters live in the
process, so across N Cloud Run instances the effective ceiling is `1200 × N`. This run used
one worker deliberately, so it demonstrates the policy, not the fleet-wide number. Making
it exact needs shared state this deployment does not have and should not grow for a
ceiling set far above legitimate use.

**It says nothing about the sandbox lane.** The two other unticked §2 boxes — the
hostile-payload suite against the real provider, and the canary-URL exfil attempt — are
untouched by this and remain owed.

**One address is one address.** An attacker rotating source addresses defeats any per-IP
limiter, which was true before this run and is documented in the module. Nothing here
claims otherwise.

## Reproducing

```bash
bench/k6/run-abuse.sh
```

Needs Docker, `k6`, and `.env.db.local` (`docs/runbooks/auth-dev.md § The local database`).
It builds its own database, publishes the catalog into it, starts a throwaway API, verifies
the trusted-caller header end to end *before* running so a failure names its own cause, and
exits non-zero if any threshold is crossed.

It is local by construction and `BASE_URL` is not an argument. These scenarios deliberately
exceed the ceilings; pointing them at a shared service would be a self-inflicted denial of
service on a control whose failure mode is silently serving stale data.
